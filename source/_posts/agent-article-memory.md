今天早上刷到 Anthropic 的文章：[The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)。之前看 Agent 的上下文工程，我更多关注的是：上下文快满了怎么办？工具返回太长怎么办？怎么让模型少读一点，又尽量不丢掉关键信息？

这篇文章让我开始关注另一个问题：**一次任务中得到的经验，怎样才能在下一次任务中可靠地复用？**

“把信息写到文件里”当然是一种办法，但写下来的可能是事实，也可能只是模型当时的猜测；今天有效的经验，换了软件版本之后也可能不再成立。存储只是起点，后面还有筛选、验证、组织和更新。

下面先梳理我对原文的理解，再结合之前设想过的机器人故障诊断工具，讨论我会怎么设计和验证。涉及具体故障和实现方案的部分都是推演，还没有实际效果数据。

## 从压缩上下文，到复用经验

我之前接触到的上下文工程手段，大致包括自动或手动压缩、裁剪工具输出、按需读取文件，以及把相对独立的任务交给子代理。

这些手段解决的问题并不完全一样，潜在的信息损失也不能一概而论：

| 手段 | 主要解决什么 | 需要注意什么 |
| --- | --- | --- |
| 上下文压缩（compaction） | 在有限窗口中继续任务 | 摘要可能遗漏约束、依据和未完成事项 |
| 工具输出裁剪 | 避免单次返回占用过多上下文 | 截断的位置可能包含关键线索，需要保留重新读取的入口 |
| 按需检索和读取 | 当前只加载相关内容 | 没被召回的内容可能根本没有进入模型视野 |
| 子代理 | 让独立任务在各自上下文中执行 | 返回主会话的摘要可能遗漏证据和分歧 |
| 持久化记忆 | 跨会话复用经验 | 旧结论可能错误、过时，或者被用在不适合的场景 |

原文对 Agent Memory 的定义有明确边界：它讨论的是从经验中获得、跨会话保留、之后可以读回的知识；本文语境中的 memory 不包括模型权重更新、单次对话内学习和 compaction。[原文：Memory notes](https://www.anthropic.com/research/components-of-agent-memory)

因此，我会把“压缩当前任务”和“提炼长期经验”分开考虑。前者需要尽量保住继续执行所需的状态；后者需要判断，这次经历里到底有什么值得以后再用。

这也让我重新理解 prompt 的作用。以前我会直觉地觉得 prompt 对 Agent 的好用程度占很大比例，但没有数据支持具体占比。更值得讨论的是：prompt 有没有要求模型保留依据、区分事实与假设，以及在证据不足时继续验证？这些要求最终有没有转化成可观察的行为？

## Dreaming 在维护什么

原文用 Dreaming 描述一种后台整理过程：Agent 回看日志、笔记等已有材料，修正错误，建立新的组织方式，并调整后续会话会读到的内容。它处理的对象可以覆盖整个记忆层级。[原文：Dreaming](https://www.anthropic.com/research/components-of-agent-memory)

### 一段经历，怎样才能变成规则

我觉得这里最容易被忽略的是：**总结得更流畅，并不意味着结论变得更可靠。**

假设一次故障处理中，Agent 重启某个服务后，设备恢复正常。如果它直接写下“遇到这类报错就重启服务”，就把一次观察升级成了通用规则。问题是，恢复也可能来自网络自行恢复，或者同时进行的其他操作。

这条记录至少应该区分三个层次：

1. **观察**：执行了什么操作，之后出现了什么现象。
2. **假设**：怀疑是什么原因，哪些证据支持或反对它。
3. **已验证规则**：通过什么检查确认结论，适用于哪些条件。

如果后台整理只是把假设写得更肯定，记忆系统就可能让同一个错误在后续任务中反复出现。所以在我的设计里，Dreaming 的输出需要保留证据入口；无法核验的内容，可以继续作为待验证假设保存。

当然，日志也不天然等于事实。工具结果、环境观察和模型自己的推测，需要能区分开。拿过去的一段推测去证明现在的另一段推测，并没有增加可信度。

### 哪些内容值得长期保存

我会先问两个问题：这条信息未来可能再次改变决策吗？重新获得它需要付出多大成本？

例如，当前设备是否在线，通常应该查询实时状态。把昨天的在线状态当成今天的依据，反而容易出错。但某型号设备在特定版本下的排查顺序、一个很难发现的兼容性限制，可能值得保存。

任务进度也可以写下来，不过它应该有自己的有效期。某次排障的“下一步检查交换机日志”，与长期知识里的“通信超时排查方法”，不应该混成一条永久规则。

对我来说，筛选记忆要同时考虑复用价值、重新获取的成本和过期风险。文件数量和记录长度只能反映存储规模，不能直接说明记忆质量。

## Wiki 的价值，取决于它帮我们省掉了什么

看到 Wiki 这一部分，我想起了之前关注过的 DeepWiki，也联想到一个想法：能不能把机器人内部排障文档组织成可导航的知识库？这里仅仅是使用方式上的联想，并不代表它们的实现机制相同。

我会先区分两类查询：

- **查一个明确事实**：某错误码是什么意思，某个参数的默认值是多少。
- **组合多个线索做判断**：同一个症状可能来自哪些原因，当前版本应该优先排查哪一条路径。

第一类问题，如果已经能通过错误码准确找到一份短文档，再增加一层 Wiki，可能只是多了一次跳转。第二类问题则可能需要组织跨文档的关系，单纯返回更多搜索片段未必足够。

因此，我更愿意让 Wiki 承担“导航和组织”的职责：解释某个主题涉及哪些文档、适用范围有什么区别、下一步应该查哪里。涉及精确参数和具体操作时，仍然回到原始文档核对。

### Wiki 比原文大，就一定没用吗

原文中有一个让我印象很深的反例：生成的 Wiki 体积超过了原始材料。[原文：Wiki 膨胀的案例](https://www.anthropic.com/research/components-of-agent-memory)

![Wiki 膨胀反例：生成的页面总体积超过原始文档](https://www-cdn.anthropic.com/images/4zrzovbb/website/ffa35479b1dea63b7948f76995b488d08854e86d-3840x2150.png)

*图源：Anthropic 原文。体积增长值得检查，但还需要判断新增内容是否带来了查询价值。*

我的第一反应是：既然比原文还大，那直接看文档不就好了？之前使用 DeepSeek harness 时，我也遇到过压缩后文本反而更长的情况，当时觉得很奇怪。不过那只是一次使用观察，不能据此判断原因，也不能推成普遍结论。

再想一下，“压缩摘要”和“知识导航”对体积的要求并不相同。给定相同计量方式，压缩后更长，需要检查压缩目标是否实现；Wiki 则可能因为增加索引、链接和术语解释而变大，同时降低查询难度。

所以我会追问：新增内容到底省掉了什么工作？如果它帮助 Agent 少翻几份无关文档、更快定位到证据，那可能值得。如果只是把原文换一种说法再写一遍，还引入一份需要同步更新的副本，收益就很可疑。

## 放到机器人故障诊断中，我会怎么设计

之前我设想过一个现场机器人故障诊断工具：机器人报错后，Agent 根据错误码或关键词查找内部解决文档，再结合现场信息给出排查建议。

这个思路的局限在于，**错误码可以作为检索入口，却未必足以确定根因。** 文档也不一定完整记录了不同版本、不同设备和多种故障共同发生时的情况。

下面以“通信超时”为假设场景，说明我会怎样进一步设计。它不是已经完成的项目案例。

### 从错误码入口，走到可验证的排查路径

假设设备报告通信超时，可能需要检查网络连接、设备重启记录或软件兼容性。此时 Wiki 如果只把相关文档全部链接过来，Agent 仍然需要自己判断先后顺序。

我希望页面能进一步组织这些信息：

| 内容 | 希望帮助 Agent 回答的问题 |
| --- | --- |
| 适用范围 | 当前设备型号、软件版本是否符合？ |
| 症状与候选原因 | 哪些原因能够解释当前现象？ |
| 排查步骤 | 先获取哪项观察，才能排除一个分支？ |
| 来源与历史工单 | 这个判断来自哪里，有没有相反案例？ |
| 未解决的问题 | 还有哪些信息不足，不能直接下结论？ |

一个简化流程可以是：

```text
错误码 + 设备型号 + 软件版本 + 现场日志
                  ↓
          检索适用的排障入口
                  ↓
       获取候选原因及其证据要求
                  ↓
        查询实时状态、核对原文
                  ↓
       排除分支，或请求补充信息
                  ↓
        给出有来源的下一步建议
```

这里需要防止“关联越多越好”的倾向。其他型号、旧版本和表面相似的工单都可能增加干扰。因此，链接最好说明关联原因，并保留型号和版本等适用条件。

### 一条经验需要保留哪些信息

如果要把一次工单的经验写回知识库，我会先用类似下面的结构。字段是设计示例，不是实际故障结论：

```yaml
topic: 通信超时排查
status: 待验证
observation: 重启相关服务后通信恢复
hypothesis: 可能与该服务状态异常有关
scope:
  device_model: 待补充
  software_version: 待补充
sources:
  - 工单编号与日志位置
verification: 尚未排除网络自行恢复等其他原因
last_verified_at: null
recheck_when:
  - 软件版本变化
  - 出现反例
```

这份记录暂时不能支持“以后遇到同样报错就重启”的结论，但能为下一次排查提供一个有出处的假设。等到补齐证据、明确适用范围，再决定是否升级成规则。

写入 Wiki 的经验也不应自动变成操作指令。查到一种历史解决方法，与确认它适用于当前设备，是两个步骤。

### 怎样验证它比直接检索更有用

我会先做一个能按错误码、型号和版本检索文档的基线，再比较增加 Wiki 之后的变化。没有这个基线，就很难判断收益来自知识组织，还是仅仅来自更好的检索条件。

可以选择同一批历史工单，让两种方案在相同输入和工具条件下处理，观察：

- **判断质量**：是否找到正确原因，或给出能够推进诊断的下一步。
- **证据质量**：结论是否有来源，引用是否真的支持结论。
- **检索负担**：读了多少无关文档，消耗多少 token 和时间。
- **版本适用性**：是否错误套用了其他版本的处理方法。
- **维护成本**：生成、核验和更新 Wiki 需要多少额外工作。

评估时，只提供诊断当时已经能获得的信息。目标工单的最终结论，以及诊断之后才形成的经验，都不能提前放进输入或 Wiki，否则可能只是让 Agent 读到了答案。

我也不会把“有没有立即给出根因”当成唯一标准。证据不足时，能明确指出缺少什么，并提出有区分度的检查步骤，也是一种有效结果。

## 记忆的读取和更新，也需要预算

除了怎么生成记忆，我还会关心两个运行中的问题：每次读多少，以及什么时候重新核验。

### 常驻上下文保留入口，细节按需读取

我的设计倾向是让常驻上下文保持短小，主要说明当前目标、关键约束，以及去哪里找相关知识。某个设备的完整排障步骤、某次工单的日志和过程，放在下层按需读取。

这样做的一个原因是，Agent 可能不知道自己曾经记录过某条经验。一个短索引能提供入口；但如果索引里塞满所有细节，每次会话都要承担它们的读取成本，还可能带入不适用的旧结论。

索引也需要维护：移除失效入口，标记适用范围，避免链接存在但目标页面已经过时。限制读取长度只是其中一个手段，更关键的是有限空间里保留了什么。

### 按变化风险安排核验

下面是我会尝试的维护策略，还需要通过实际使用验证：

| 信息类型 | 更新或核验方式 |
| --- | --- |
| 当前设备状态、任务进度 | 优先查实时来源，任务结束后清理或归档 |
| 版本相关配置和兼容性 | 在版本升级、文档变化时重新核验 |
| 高频使用的排障经验 | 结合使用反馈检查，出现反例时降低可信度 |
| 相对稳定的背景知识 | 降低核验频率，同时保留来源 |

如果文档已经更新，对应页面也应该能找到受影响的结论。否则，只做定期“重新总结”，很难知道哪些旧经验需要撤回。

至于什么时候写记忆，我倾向于在任务中先记下必要的证据入口和待验证问题，避免频繁整理打断排查；在阶段结束后，再做合并、核验和索引更新。需要马上供后续步骤使用的关键状态，则不能等后台任务处理完。

## 我想先验证的几个判断

读完之后，我对 Agent Memory 最感兴趣的地方，是它如何把一次性的处理过程变成可复用、可回查、也可撤回的经验。

放到机器人故障诊断里，我会先验证三件事：跨文档组织是否真的帮助选择排查路径；给经验保留来源和适用范围，是否减少误用；这些收益能否覆盖知识维护的成本。

如果准确检索一份文档就能解决问题，就先把检索做好。如果多份文档之间的关系才是难点，再尝试 Wiki。遇到一次成功处理，先保存观察和证据，再决定它是否足以成为规则。

这也是我接下来更想关注的上下文工程问题：Agent 能否在需要的时候找到经验、判断经验是否适用，并在发现反例后及时改掉它。
