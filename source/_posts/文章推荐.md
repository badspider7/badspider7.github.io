最近在看 Agent 和 LLM 相关的资料，顺手收藏了不少文章、文档和开源项目，分享出来，可以时不时回味一下，也会不断补充。

<!-- more -->

## 如果刚开始，可以按这个顺序看

1. **先建立基本认识**：看 Karpathy 的大模型讲解，再读 Claude Code 的工作原理，区分模型本身的能力和 Agent 外围程序做的事情。
2. **把工具用顺手**：了解项目指令、提示词和 Skills，拿一个小任务试试，比如修复报错或补充测试。
3. **理解上下文怎么组织**：读 Manus 和 Cursor 的文章，看看文件、工具结果、历史记录是怎样进入模型上下文的。
4. **找一个项目动手**：从客服 Demo、开源编码 Agent 或规范驱动开发工具中选一个，跑通最小流程，再研究实现。

如果已经用过一段时间 AI 编程工具，可以直接从“上下文工程”这一节开始。

## 一、入门：先理解模型与 Agent

### Karpathy：深入探索像 ChatGPT 这样的大语言模型

[视频：安德烈·卡帕西——深入探索像 ChatGPT 这样的大语言模型](https://www.bilibili.com/video/BV16cNEeXEer/)

很好的入门LLM的视频，将了一个model的大致步骤，从数据清洗，预训练，基模到后训练；上手也不难，可以白嫖 google的卡 去训练一个小的模型。作为一个了解 大模型是怎么产生的还是很不错的，后续还可以深入 机器学习，强化学习等。

### Claude Code 是怎么工作的

[How Claude Code works · 官方文档](https://code.claude.com/docs/en/how-claude-code-works)

这篇适合用来理解编码 Agent 的基本工作方式：收集上下文、采取行动、检查结果，再根据反馈继续下一轮。读的时候，可以对照一次实际任务，看看它什么时候读文件、什么时候调用工具，以及拿到结果后如何继续。

建议重点关注：**一个任务能不能完成，除了模型回答得好不好，还取决于它能获取哪些信息、使用哪些工具，以及怎么验证结果。**

## 二、日常使用：让 Agent 更了解项目

### Claude Code 最佳实践

[Claude Code 最佳实践 · 官方文档](https://code.claude.com/docs/zh-CN/best-practices)

已经开始用 Claude Code，但效果有时好、有时差，可以先看这一篇。重点是把项目里隐含的信息说清楚，并给出可以运行的检查方式。

例如“帮我修好这个接口”还不够具体，可以补上复现步骤、预期行为和测试命令。读完后挑一个手头的小任务，比较补充这些信息前后的结果，比单纯收藏技巧更有帮助。

### `.claude` 目录里都放了什么

[探索 .claude 目录 · 官方文档](https://code.claude.com/docs/zh-CN/claude-directory)

项目指令、个人设置、Skills、Hooks 等内容容易混在一起。这篇可以当作配置入口的索引，在需要时查对应文件放在哪里、作用范围是什么。

建议先分清项目配置和个人配置，再按需要添加内容。多人协作时，尤其可以想一下：哪些约定应该跟随仓库共享，哪些只是自己的使用偏好？

### 提示词设计

[提示词设计 · Cursor 博客](https://cursor.com/cn/blog/prompt-design)

这是一篇较早的文章，用网页设计类比提示词设计，讨论清晰表达、动态输入、内容组合和上下文空间限制。部分背景有时代性，但“查看最终拼出来的提示词”这个思路仍值得借鉴。

如果在做自己的 Agent，可以检查一下：模板加上用户输入、项目说明和工具结果后，模型实际收到的内容是否清楚？有没有重复、冲突，或者关键要求被埋在大段日志里？

### Skills：把重复任务整理成可复用的流程

[Agent Skills · Cursor 官方文档](https://cursor.com/docs/skills)

Skills 可以用文件组织特定任务的说明，并附带相关脚本或资源。适合拿来思考：哪些经常重复的工作，值得从临时对话整理成可复用的流程？

可以先选一个范围明确的任务，例如按项目规范写提交说明、执行固定检查，写清楚适用场景、输入和完成标准，再观察实际使用时还缺什么。

## 三、上下文工程：让 Agent 在需要时拿到信息

### Claude Code 的上下文窗口

[探索上下文窗口 · 官方文档](https://code.claude.com/docs/zh-CN/context-window)

这篇用交互式演示说明会话中的内容如何占用上下文：项目指令、读取的文件、工具结果和历史消息都会参与其中，还涉及压缩后哪些内容会保留或重新加载。

适合先建立一个直观认识：一次任务里，模型看到的内容会不断变化。遇到长任务效果下降时，可以先检查窗口里装了什么，再考虑调整加载和压缩方式。

### Manus：构建 Agent 时的上下文工程经验

[AI 代理的上下文工程：构建 Manus 的经验教训](https://manus.im/zh-cn/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

这篇把视角放到 Agent 的工程实现。适合带着一个具体问题读：Agent 连续执行很多步以后，哪些信息应该继续带着，哪些适合放到文件里按需读取？

阅读时可以把文中的经验和自己的任务对照起来，记录一个可以验证的改进点。来自特定产品的实践，迁移到自己的工具和运行环境后，还需要观察实际效果。

### Cursor：动态发现上下文

[Dynamic context discovery · Cursor 博客](https://cursor.com/blog/dynamic-context-discovery)

这篇介绍了把较长的工具输出、聊天历史和终端输出保存为文件，让 Agent 按需查找的做法，也讨论了 Skills 和 MCP 工具描述的动态加载。

值得关注的是它处理长输出的方式：保留可以回查的完整内容，再让 Agent 读取相关部分。自己实现时，可以观察这是否减少了重复加载，以及 Agent 能否在需要时找回关键细节。

### 代码仓库索引：延伸阅读

[How Cursor Actually Indexes Your Codebase · Towards Data Science](https://towardsdatascience.com/how-cursor-actually-indexes-your-codebase/)

这是一篇第三方分析，可以作为理解代码库索引的补充入口。阅读时可以关注代码切分、检索和上下文选择之间的关系；涉及 Cursor 当前实现的细节，仍应以官方资料和可验证的行为为准。

## 四、工程实践：控制执行过程，观察运行结果

### Hooks：在执行节点加入处理逻辑

[使用 Hooks 拦截和控制代理行为 · Claude Agent SDK 文档](https://code.claude.com/docs/zh-CN/agent-sdk/hooks)

这里介绍的是 **Agent SDK 的 Hooks**，适合正在用 SDK 构建 Agent 的朋友。它通过事件回调，在工具执行前后或会话生命周期的相应节点运行处理逻辑。

可以重点看三个问题：如何拦截一次不允许的工具调用，如何记录执行结果，以及如何根据事件补充上下文。实际接入时，要核对所用 SDK 版本对应的事件和返回格式。

### OpenTelemetry：看清 Agent 的运行过程

[使用 OpenTelemetry 进行可观测性 · Claude Agent SDK 文档](https://code.claude.com/docs/zh-CN/agent-sdk/observability)

当 Agent 能跑起来之后，通常还需要知道：时间花在哪里、调用了哪些工具、消耗了多少 token，以及失败发生在哪一步。这篇介绍如何把相关遥测数据导出到支持 OTLP 的后端。

适合从一次具体的失败任务开始：沿着记录回看每一步，判断问题出在模型请求、工具执行，还是结果处理，再决定如何改进。

### Cursor：走向自主运行的代码库

[Towards self-driving codebases · Cursor 博客](https://cursor.com/blog/self-driving-codebases)

这篇介绍了长时间运行、多 Agent 编码系统的实验和架构演变，涉及任务分工、执行反馈、协作开销和正确性之间的取舍。

推荐关注尝试失败的部分：简单共享状态为什么会产生协调问题，一个角色承担太多职责又会发生什么。它是研究场景中的工程记录，适合借鉴问题和取舍，再判断自己的任务是否需要类似架构。

## 五、开源项目与工具：选一个动手试试

### DeepWiki：阅读开源项目的辅助入口

[DeepWiki](https://deepwiki.com/)

强力推荐用来辅助了解陌生仓库。可以先通过项目文档和问答建立整体认识，再回到源码确认具体实现。

比如先问“这个项目的主要模块是什么”“某个功能的入口在哪里”，再沿着文件和调用关系往下看。涉及重要结论时，最好把相关代码、测试或运行结果一起对照起来。

### 几个值得研究的项目

| 项目 | 定位 | 可以带着什么问题看 |
| --- | --- | --- |
| [Dyad](https://github.com/dyad-sh/dyad) | 本地运行的开源 AI 应用构建工具 | 从用户需求到应用生成，产品把哪些步骤串了起来？ |
| [OpenCode](https://github.com/anomalyco/opencode) | 开源编码 Agent | 一次编码任务如何组织模型交互、工具执行和结果反馈？ |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec) | 面向 AI 编程助手的规范驱动开发工具 | 如何在实现前把需求和变更范围写清楚，并在后续核对？ |
| [OpenAI Support Agent Demo](https://github.com/openai/openai-support-agent-demo) | 使用 Next.js、Responses API 和 File Search 的客服界面示例 | 知识检索和对话界面如何接起来，答案怎样呈现给用户？ |

不用同时跑完这些项目。挑一个和当前需求最接近的，先按 README 跑通最小流程，再沿着一次请求追踪实现，会更容易看懂。

### 钉钉生态：连接实际业务工具

- [钉钉 AI Hub MCP 入口](https://aihub.dingtalk.com/#/mcp)：适合查找钉钉生态的 MCP 接入入口，具体能力和接入要求以页面说明为准。
- [DingTalk Workspace CLI](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli)：钉钉官方开源的跨平台命令行工具，面向人工操作和 AI Agent 场景。

如果想做办公场景的 Agent，可以从一个小需求开始，比较 MCP 和 CLI 两种接入方式需要怎样配置、返回什么结果，以及哪一种更适合自己的运行环境。

## 六、博客与业务案例补充

- [rustc.cloud](https://www.rustc.cloud)：保留一个博客入口，感兴趣可以按自己的方向挑文章阅读。
- [基于大模型 + 知识库的 Code Review 实践](https://www.rustc.cloud/cr-copilot#06bf9fca7bce4303b2ddf925243cb3ab)：一个 Code Review 方向的案例入口。可以带着“项目知识怎么提供给模型”“生成的建议怎么验证”这两个问题阅读。

看业务案例时，建议多追问一步：它解决的具体问题是什么，效果是怎么判断的，换到自己的项目还缺哪些条件？这样更容易把文章里的思路变成可以尝试的方案。

## 最后：读完之后，留一个能验证的结果

资料会越来越多，可以给自己定一个小目标：每读完一篇，至少回答一个原来没想清楚的问题，或者在项目里做一次小实验。

比如读完上下文工程，检查一次任务里是否反复携带了无用日志；读完 Skills，整理一个自己每周都会重复的流程；读完可观测性，尝试把一次失败的执行过程查清楚。

Agent 是一个变化很快的方向。这份清单也会继续补充，希望能以兴趣为导向，一边学习，一边实践。

最后，借用史蒂夫·乔布斯引用过的那句话：

> Stay hungry. Stay foolish.
>
> 求知若饥，虚心若愚。
