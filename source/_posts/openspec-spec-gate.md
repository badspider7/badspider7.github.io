今年上半年，我们在做一个 AI Coding 工具：让产品、运营也能把一段需求变成能跑、能测的前端项目。

最早的做法很直接：把需求丢给 Agent，让它生成代码。试了两周，问题很集中——页面能打开，但字段少了、空状态没处理、权限判断写反了。你问它为什么，它会说“我理解的需求是这样”。

我们后来才想明白：不是模型不会写代码，是“写之前没有把需求和验收对齐”。于是开始找 spec 工具，最后选了 OpenSpec，又在它上面加了一道自己的门禁。

这篇按“它是什么 → 我们遇到什么问题 → 为什么选它 → 用了之后解决了什么 → 还缺什么”来讲。

<!-- more -->

## 背景：我们在做什么

这个工具面向的不是专业前端。需求方给的往往是 PRD、接口文档和一句“照着这个做”，有时甚至是口述。

通用 Coding Agent 的工作方式是“边猜边写”，适合探索，不适合交付。交付需要三个东西：

- 写之前，需求、边界、验收是确认过的；
- 写完，有独立的测试判断是否通过；
- 改坏了，能回滚，能定位是哪一步出的问题。

我们一开始试过“在 prompt 里要求先写需求”，也试过自己定一套 Markdown 模板。问题是：格式能统一，但 Agent 还是会跳过、漏项，而且不同项目各写各的，没法复用。

## OpenSpec 是什么

[OpenSpec](https://github.com/Fission-AI/OpenSpec) 是一个轻量的、可配置的 spec 框架，面向 AI Coding 场景。它把一次变更拆成几份 Markdown：

```text
changes/<change-name>/
├─ proposal.md   为什么改、改什么
├─ design.md     技术方案/取舍
├─ tasks.md      任务拆解
└─ specs/        本次变更的 spec delta

specs/<domain>/
└─ spec.md       系统当前行为的“事实源”
```

它的工作流大致是：

```text
explore → propose → apply → verify → archive
```

也就是先探索问题和代码库，再产出提案/spec/设计/任务，然后按 spec 实现，最后验证实现和 spec 是否一致，归档这次变更。

它支持 Claude Code、Codex、Cursor 等一批 Agent CLI，MIT 协议，文档在 [openspec.dev/docs](https://openspec.dev/docs)。

## 为什么选它，而不是自己写模板

我们不是因为它火才用，是因为它刚好适配我们的场景。

### 1. 它是 Markdown，能进 Git

spec、design、tasks 都是普通 Markdown，可以提交、可以 diff、可以在 PR 里 review。我们不需要再做一个“需求管理平台”。

### 2. 它按“变更”组织，适合存量项目

`specs/` 描述系统当前行为，`changes/` 描述这次要改什么。对老项目很友好：不用先把整个系统文档补全，只补这次变更涉及的部分。

### 3. 它足够轻，不绑流程

有些 spec 框架会带一整套角色、阶段、模板，落地成本很高。OpenSpec 的哲学是“流动而非僵化”，你可以只用它的目录结构和命令，也可以按自己的业务加模板。

### 4. 它能接我们已经在用的 Agent CLI

我们不想为了一个 spec 工具换掉 Agent。OpenSpec 支持多种 CLI，接入成本低。

### 5. 它能改

这是最关键的。通用模板不一定适合我们的需求方，我们可以加字段、加校验、加门禁。它不是黑盒。

## 用了之后，解决了什么

最直接的变化是：**需求从“聊天记录”变成了“可 review 的文件”。**

以前 Agent 写完代码，你只能看结果；现在可以先看 `proposal` 和 `spec`，在写代码之前把“做什么、不做什么、怎么验收”对一遍。

第二个变化是**可追溯**。一次变更对应一个目录，里面有 proposal、design、tasks、spec delta。出了问题，能回看当时是怎么想的，而不是翻聊天记录。

第三个变化是**复用**。模板、检查项、验收格式可以沉淀下来，下个项目不用从零写 prompt。

但它只解决了“有 spec”，没解决“spec 有没有被确认”。

## 它还不够：Agent 会从草案直接进实现

我们遇到过一个很典型的例子：给配置页加一个开关。spec 写得很顺：

```md
## 需求
在配置页增加“启用自动同步”开关。

## 验收
- 开关可以打开/关闭
- 保存后生效
```

至少还有五个问题没答案：

- 配置缺失时，默认开还是关？
- 没有权限的用户，能看到开关吗？
- 保存失败时，开关状态回滚吗？
- 切换要不要二次确认？
- 这个开关影响当前项目还是全局？

Agent 不会停下来问。它会选一个“最合理”的默认值，然后一路写下去。等页面做完，需求方说“不对，默认应该是关的”，改的就不只是一个布尔值，还有接口默认值、表单初始状态、权限分支和测试用例。

OpenSpec 默认人和 Agent 会自觉 review。实际不会。人看到一份结构完整的 spec，很容易回一句“可以”，然后 Agent 就开始写了。

## 所以我们加了一道门禁

在 spec 和实现之间，我们加了一层审核门禁。它不是一句“请先确认”的 prompt，而是有状态的：

```text
Draft → Waiting for approval → Approved → Implementation
```

在 `Waiting for approval` 状态，Agent 不允许调用写文件的工具，也不允许开始实现。它只能做三件事：

1. 输出草案摘要；
2. 列出待确认问题和假设；
3. 等待明确批准。

什么算“明确批准”？我们写死了几个词：

```md
- 已批准
- 可以开始实现
- 按这个做
- 批准，但按这些修改后再做
```

“可以”“还行”“你先做吧”都不算。听起来死板，但这是被坑出来的：之前有人说“可以”，Agent 理解成批准，写完才发现对方只是说“我看到了”。

## 业务化的 spec 模板

除了门禁，我们还把 OpenSpec 的模板按业务改了。通用模板偏“功能描述”，我们补了几块：

```md
## 角色与入口
- 谁使用：一线工程师 / 产品经理 / 运营
- 从哪里进：IM / Web / 客户端
- 前置条件：登录、权限、数据状态

## 主流程与异常
- 正常路径
- 空数据 / 无权限 / 接口失败 / 超时
- 重复提交 / 并发操作

## 数据与权限
- 读写哪些表/接口
- 哪些字段敏感
- 跨部门是否可见

## 验收标准
- 可观察的页面结果
- 可执行的测试步骤
- 不做什么（非目标）

## 待确认假设
- Agent 自己补的默认值/边界
```

最后一项“待确认假设”是我觉得最有用的。它强迫 Agent 把“我猜的”写出来，而不是混在需求里。人 review 的时候，先看这一节，通常就能发现大部分问题。

## 门禁也要分级

一开始我们对所有需求都卡门禁，结果小改动也被卡：

> 把按钮文案从“提交”改成“保存”。

这种改动也要写 spec、等批准，需求方直接骂人。

后来我们做了分级：

- **L0 文案/样式**：跳过门禁，直接改；
- **L1 单页面交互**：轻量 spec + 一次性确认；
- **L2 跨页面/接口/权限**：完整 spec + 门禁；
- **L3 数据/权限/迁移**：完整 spec + 门禁 + 人工 review。

分级不是按代码行数，而是按“改错的代价”。文案改错，改回来就行；权限改错，可能是生产事故。

## 结果和边界

最直观的变化是返工少了，但一次做对的概率高了。

以前一个页面做完，需求方提一堆“这里不对”，Agent 再改一轮；现在很多问题在 spec 阶段就被问出来了。代价是前期多花 10–20 分钟，但省掉了后面一两轮返工。

测试用例的质量也跟着变了。spec 里的验收标准越具体，生成的 Playwright 用例越可用。以前只能写“打开页面，点击按钮，页面正常”，现在能写“无权限用户看不到开关；保存失败时开关回滚到原状态”。

不过门禁不是万能的：

- 它只能拦住“写代码之前”，拦不住实现阶段的新歧义；
- 需求方如果懒得看，还是会回“可以”；
- 分级规则需要持续调，太松没效果，太紧没人用。

OpenSpec 提供的是“结构”，我们补的是“约束”。结构让 Agent 不瞎写，约束让 Agent 在没想清楚的时候停下来。

如果你也在做 Spec 驱动的 Agent，我的建议是：先想清楚你的场景缺的是“格式”还是“确认”。缺格式，OpenSpec 这类框架能帮上忙；缺确认，就得自己在流程上加门禁。
