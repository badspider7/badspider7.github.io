平台不是一开始就有的。

最早每个业务都自己接模型、自己写工具、自己处理会话。邮件处理 Agent 有一套记忆，知识问答 Agent 又有一套；IM 里这个机器人能回、那个机器人不回；出了问题只能去翻各自的服务日志。重复建设不说，最麻烦的是没有统一的权限和入口。

后来我们把共性收出来，做了一个云端 Agent 平台。它不直接跑模型，管的是“谁可以跑、跑什么、跑到哪了、花了多少”。这篇拆一下它的结构，以及几个当时没想清楚、后来补的坑。

## 背景：为什么要多一层平台

如果只有一个 Agent，直接在业务服务里调模型最简单。

但当 Agent 变成十几个，问题会变成：

- 每个 Agent 都要接一遍模型、工具、会话、权限；
- 同一个业务能力，在三个 Agent 里重复实现；
- 用户不知道去哪个入口找哪个 Agent；
- 出问题没有统一的执行轨迹；
- 换模型、改 Prompt 没有统一的地方。

平台的价值不是“多一层”，是把这些共性收口。代价也很明显：多了一层，链路更长，排查更麻烦。

## 四个角色

拆开看，大概是：

```text
Web / IM
   │
   ▼
Agent Server
├─ Agent 注册 / 配置 / 权限
├─ 会话 / 任务路由
├─ 任务状态机 / 消息 / 用量
└─ WebSocket / 事件推送
   │
   ▼
Daemon（跑在用户机器或云端）
├─ 拉取任务
├─ 启动 Agent CLI
├─ 解析执行事件
└─ 回传消息 / 用量 / 结果
   │
   ▼
Agent CLI（真正干活的那个）
```

Server 不直接跑模型。Daemon 是执行器，负责把任务交给具体的 Agent CLI，再把过程流回 Server。

这个拆分看起来多了一层，但很值：Agent CLI 可以换、模型可以换、执行机器可以扩，Server 只负责平台能力。

## 一条任务的生命周期

平台里最重要的对象不是 Agent，是 Task。

一条任务大概会经历：

```text
queued → dispatched → running
  → progress / message / usage
  → completed / failed / cancelled
```

其中“消息”是执行轨迹，通常有几种类型：

- `text`：Agent 输出的文本；
- `tool_use`：调用了什么工具、入参是什么；
- `tool_result`：工具返回了什么；
- `error`：执行过程中出现的错误。

“用量”则是另一条线：provider、model、input/output tokens、cache tokens、成本。它和消息分开，因为一个是过程，一个是账。

这几个事件看起来简单，但平台的大部分坑都和它们有关：

- 消息会乱序，前端不能假设序号一定连续；
- 任务会重试，同一个任务可能有多轮执行；
- 会话会重建，旧的会话绑定可能已经归档；
- Webhook 会丢，轮询会重复，必须做幂等和补偿。

我们后来把“轮询 + Webhook + Push”三种方式叠在一起，不是因为喜欢复杂，而是只靠一种方式，总有一种场景会漏。

## Agent 是六层配置，不是一个 prompt

平台里的 Agent 不是一段系统提示词，而是一组配置：

```text
Agent
├─ Model        用哪个 provider / model
├─ Harness      用什么 Agent CLI / 运行参数
├─ Tool         能调哪些工具
├─ Skill        会哪些业务能力
├─ Memory       上下文/记忆怎么管
└─ Permission   谁能用、能用哪些工具
```

这六层拆开之后，业务方不需要写代码：选模型、挂 Skill、配权限、绑定入口，几分钟能发布一个能用的 Agent。

但抽象是有代价的。最早我们想把所有东西都塞进“Agent 配置”，结果配置越来越像一门 DSL，业务方看不懂，开发也难维护。后来砍了一轮，只保留真正需要业务方决策的字段，其他全部走默认值。

平台设计最容易犯的错，是把“可配置”当成“什么都让用户配”。

## IM 入口比想象中脏

Agent 能力做得再好，业务人员不打开 Web 页面，就等于没有。所以 IM 入口是平台的关键。

链路大概是：

```text
IM @机器人
  → 接入层接收消息
  → 平台做意图识别 / 权限 / 会话解析
  → Agent 执行
  → 结果回调
  → IM 消息 / 互动卡片
```

最麻烦的是互动卡片：

- 卡片有表单、下拉、按钮，回调参数结构不一样；
- 用户可能在会话切换后点上一张卡片，回调要能找到正确的会话；
- 卡片可以“回刷”，公共数据和私有数据的写入时机不同；
- 同一个按钮可能被重复点击，必须做幂等；
- 卡片发送失败、消息太长、附件上传失败，都要有降级。

我们在这块花了很久。最后的原则是：**卡片回调不猜业务语义，只做参数透传和路由**。卡片里的字段含义由 Agent 自己解释，平台只保证“这张卡属于哪个会话、哪个用户、哪个任务”。

## 多 Agent 小队：交接的契约比“智能”重要

单个 Agent 再强，也有边界。一个 Coding Agent 既写代码又写测试又验收，很容易“自己判自己赢”。

平台后来支持人和 Agent 混编的小队，由一个 Leader 把任务分给合适的角色。我们用它组了实现 / 测试 / 评审的小队：

```text
任务
  → Leader 分派
  → 实现 Agent 写代码
  → 测试 Agent 执行
  → 失败：回传实现 Agent 修复
  → 评审 Agent 检查
  → 人确认合并
```

关键不是“多 Agent”，而是交接的契约：

- 失败报告要结构化：哪一步、哪个用例、什么错误、截图/日志在哪；
- 轮次要有限制：测试和修复都有上限；
- 状态要能回放：谁在什么时候改了什么；
- 人要能随时接管：不是所有失败都值得让 Agent 继续试。

如果没有这些约束，多 Agent 只会把一个小问题变成一群 Agent 的聊天记录。

## 现在回头看

做得对的：

- 先做任务/消息/用量，再做 Agent 编排。没有执行轨迹，编排就是黑盒；
- 把 IM 入口当一等公民。业务人员不会为了用 Agent 专门开一个系统；
- 权限和会话绑定放在平台层，不让每个 Agent 自己实现一套。

做得不对的：

- 一开始过度设计配置，业务方学不会；
- 太晚做可观测，出问题只能靠猜；
- 卡片回调的幂等做得太晚，重复点击导致重复任务；
- 把“多 Agent”当成目标，而不是手段。

平台现在还不能说完善。但至少它把 Agent 从“一个会聊天的接口”变成了“有任务、有权限、有轨迹、有交接的运行时”。这一步不性感，却是所有业务 Agent 能真正跑起来的前提。
