去年底我们在做一个工具：让产品经理和后端也能把一个页面需求变成能跑、能测、能交付的前端项目。

一开始的想法很简单：接一个 Coding Agent，把 PRD 丢进去，让它生成代码。试了两周就发现不行。页面确实能打开，但字段少了、空状态没处理、权限判断写反了。你问它为什么，它会说“我理解的需求是这样”。

问题不在模型会不会写代码，而在“写之前有没有把需求和验收对齐”。后来这个工具慢慢变成了一条流水线：Spec、任务拆解、代码、测试、修复。下面记录几个关键设计，以及我们现在还没解决的地方。

## 背景：为什么不是“聊天框 + 代码生成”

我们的需求方大多不是专业前端，给的是 PRD、接口文档和一句“照着这个做”。通用 Coding Agent 的工作方式是“边猜边写”，适合探索，不适合交付。

交付需要三个东西：

- 写之前，需求和边界是确认过的；
- 写完，有独立的测试来判断是否通过；
- 改坏了，能回滚，能定位是哪一步出的问题。

所以这个工具的核心不是“生成”，是“约束”。

## Spec 不是文档，是契约

我们用了 OpenSpec 的结构：`proposal`、`design`、`tasks`，以及按领域拆的 spec。Agent 先产出 spec，再拆任务，最后写代码。

但只引入 OpenSpec 还不够。它解决“有一份结构化的 spec”，不解决“spec 没写清楚时，Agent 会不会硬着头皮往下写”。

我们遇到过一个很典型的例子：给配置页加一个开关。spec 写得很顺：

```md
## 需求
在配置页增加“启用自动同步”开关。

## 验收
- 开关可以打开/关闭
- 保存后生效
```

至少还有五个问题没答案：

- 配置缺失时，默认开还是关？
- 没有权限的用户，能看到开关吗？
- 保存失败时，开关状态回滚吗？
- 切换要不要二次确认？
- 这个开关影响当前项目还是全局？

Agent 不会停下来问。它会选一个“最合理”的默认值，然后一路写下去。等页面做完再发现，改的就不只是一个布尔值，还有接口默认值、表单初始状态、权限分支和测试用例。

## 加一道“不准写代码”的门禁

我们基于 OpenSpec 做了一层业务定制：在 spec 产出之后、代码实现之前，加一个阻塞状态。

```text
Draft → Waiting for approval → Approved → Implementation
```

在 `Waiting for approval` 状态，Agent 不能调用写文件的工具，只能做三件事：

1. 输出草案摘要；
2. 列出待确认问题和假设；
3. 等待明确批准。

什么算明确批准？我们写死了几个词：

```md
- 已批准
- 可以开始实现
- 按这个做
- 批准，但按这些修改后再做
```

“可以”“还行”“你先做吧”都不算。听起来死板，但这是被坑出来的：之前有人说“可以”，Agent 理解成批准，写完才发现对方只是说“我看到了”。

另外，spec 模板里必须有“待确认假设”这一节。Agent 自己补的默认值、边界、异常处理，都要单独列出来，不能混在需求里。

## 测试不能由写代码的 Agent 自己判

Spec 对齐之后，第二个问题是：谁来验收？

如果让 Coding Agent 自己写测试、自己跑、自己说“通过了”，等于没测。它很容易写一个刚好能过的用例，或者把失败的断言改掉。

我们的做法是拆成三个角色：

1. **测试用例生成 Agent**：基于 PRD、代码 Diff 和页面源码，生成带 Playwright locator 的 Markdown 用例；
2. **测试 Agent**：在 CI 里执行用例，输出失败报告；
3. **Coding Agent**：根据失败报告修代码，修完通知测试 Agent 回归。

测试用例有一条硬约束：每个被操作或断言的元素，必须有经源码确认的 Playwright locator；没有可靠依据就标“待补充”，禁止臆造选择器。

闭环大概是这样：

```text
Coding Agent 提交代码
  → CI 创建测试任务
  → 测试 Agent 执行 Playwright 用例
  → 失败：回传失败步骤、截图、日志
  → Coding Agent 修复，提交新 Commit
  → 测试 Agent 回归
  → 全部通过：在 Commit 里回写报告
```

为了防止两个 Agent 互相踢皮球，测试和修复都有轮次上限：测试最多 5 轮，修复最多 3 轮，超过就停下来让人介入。Commit 里也会标记这是修复提交还是普通提交，避免 CI 把同一个修复反复当成新任务。

## 元素点选：把“改哪里”变成坐标

还有一个功能我觉得比“换更强的模型”更有用：在预览窗口里直接点页面元素，让 Agent 改这个元素。

普通 Coding Agent 的粒度是文件/对话。你说“把这个按钮改成蓝色”，它要去搜 `button`、找 className、猜是哪个组件。页面一复杂，很容易改错文件。

元素点选的链路是：

```text
预览 iframe
  → 点击 DOM
  → 拿到组件链/选择器
  → 映射到源码文件 + 行号
  → 把「元素 + 文件 + 行号 + 当前代码」一起给模型
```

模型不需要全页搜索，修改意图直接落到某个元素上。对组件多、命名乱的项目，收益很明显。

它也有边界：动态渲染、跨 iframe、Canvas 里的元素拿不到，只能降级成“选中区域 + 截图 + 描述”。

## 上下文和回滚

长任务最大的敌人是上下文膨胀。工具结果越堆越多，模型开始忘事，或者把很早之前的代码当成当前代码。

我们做了几件事：

- 工具结果裁剪：大文件、命令输出只保留摘要和关键片段；
- 上下文压缩：到阈值后把历史压成摘要，保留最近几轮和关键约束；
- Checkpoint：把 Git Commit 和对话消息绑定，回退代码时同步裁剪后续对话。

Checkpoint 踩过坑。最开始只回退代码，不回退对话，模型还在用“回退前”的上下文，修出来的东西和代码对不上。后来改成应用级互斥锁串行化回退，用新增 Commit 恢复历史代码，同时裁掉后续消息，才稳定。

## 现在的状态

这套东西目前能把一个页面需求从“按天”压到“按半天”，但我不觉得它已经成熟。

还没解决好的：

- 测试用例质量依赖 PRD 和页面源码，PRD 写得糊，用例就糊；
- Playwright 在复杂交互下还是会 flaky；
- 只能看到任务级的 token/成本，做不到每次模型调用的 per-call trace；
- 门禁会拖慢小改动，我们还在做“什么级别的改动可以跳过”的分级。

如果重来一次，我会更早把评测集建起来。不是等产品做完再补，而是在第一批项目交付时就把“哪些任务算成功、哪些算返工”记录下来。否则后面所有“效果不错”都是感觉，不是数据。
